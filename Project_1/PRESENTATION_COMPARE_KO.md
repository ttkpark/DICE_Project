작성 2026-11-10. 발표 슬라이드를 만들 때 그대로 옮겨 쓸 수 있게 수치와 근거 파일을 한 곳에 모았다.

## 2. ASM: 무엇을 바꿨나

근거: `starter_giho/ASM_OPT_REPORT_KO.md`, `starter_giho/int8_opt64.s`

### 2.1 프로그램 4종 (공개 16 case 평균)

| 프로그램 | word (IMEM 매크로) | 단일 cycle | 파이프라인 cycle | load+store | cycle 식 |
|---|---:|---:|---:|---:|---|
| `baseline_int8_fc_slow` (배포 기준본) | 57 (64) | 8,135.7 | 12,170.1 | 147 | W 크기에 비례 |
| `int8_small` | 48 (64) | 729.5 | 929.2 | 55 | `609 + 4p` |
| **`int8_opt64`** | **58 (64)** | **677.9** | **821.4** | **55** | `554 + 4p + n` |
| `int8_fast` | 192 (256) | 552.5 | 636.2 | 55 | `432 + 4p` |

`p` = X 8개의 1-비트 수 합(평균 32), `n` = 음수 X 개수.
파이프라인 cycle은 모두 RTL 실측이다. `int8_opt64`의 821.4는 보고서의 추정치와 정확히 일치했다 (2026-11-10 로컬 ModelSim).

### 2.2 변경 포인트

| # | 변경 | 효과 |
|---|---|---|
| 1 | **곱셈 방식**: `|W|`번 반복 덧셈 → X의 비트를 하나씩 검사해 `W<<k`를 더함 (부호 비트는 뺌) | cycle이 W 크기와 무관해짐. 8,135.7 → 729.5 |
| 2 | **비트 검사 공유**: X[i]의 비트 검사 1번을 출력 4개(j=0..3)가 같이 씀 | (i,j) 쌍당 약 10 cycle |
| 3 | **누산기를 BIAS로 시작**, 곱을 SCRATCH에 저장하지 않음 | store 37 → 5회, load 110 → 50회 |
| 4 | **비트 루프 2비트 펼침** + 종료 검사를 두 비트 사이에 배치 (`int8_opt64`) | i당 분기 13 → 7회. small 대비 단일 −7.1 %, 파이프라인 −11.6 % |
| 5 | 부호 비트가 0이면 바로 다음 i로 분기, 설정 블록을 `lw xN, 768(x0)`로 직접 읽기 | 소폭 감소 |
| 6 | **`lw` 다음 명령이 그 결과를 쓰지 않게 배치** | 파이프라인 lw-use stall 0회 |

### 2.3 한계와 기각안 (질의응답 대비)

- 기본 8명령만으로의 하한은 약 `412 + 4p`이고 그러려면 353 word(512 매크로)가 필요하다. 64 word 안에서는 `int8_opt64`가 사실상 한계다 (남은 word 6개).
- 선택 명령(SLLI, BNE 등)은 기각: doubling과 비트 검사가 이미 1명령 1 cycle이라 루프당 1 cycle만 줄고 디코더·검증 부담이 는다.
- 분기 없는 비트 검사는 비트당 10 cycle 고정이라 분기(평균 4~5 cycle)보다 느리다.

## 3. CPU: 버전별 비교

### 3.1 SINGLE (단일 사이클, `참고/1020_RISC`)

배포 기준 CORE 그대로. TOP 연결 4개와 CONTROLLER만 작성했다.

| 주기 | setup slack | hold slack | cell area (µm²) | 동적 + 누설 (mW) |
|---:|---:|---:|---:|---:|
| 5.0 | 0.00 | 0.15 | 16,526 | 1.503 + 0.909 |
| **4.0** | **0.00** | 0.15 | **17,397** | **2.051 + 0.945** |
| 3.5 | −0.01 | 0.15 | 17,274 | 2.506 + 0.988 |
| 3.0 | −0.53 | 0.16 | 19,607 | |
| 2.5 | −1.03 | 0.15 | 18,625 | |

- **선언 가능 주기 4.0 ns (250 MHz)**. 3.5 ns는 0.01 ns 모자란다.
- **Critical path**: `INSTR` 입력 → CONTROLLER 디코드(IMMSRC) → immediate mux → 32b adder → `ALURESULT` 출력.
- 논리는 1.4 ns뿐이고 **입력 delay 1.00 + 출력 delay 1.00 + uncertainty 0.10 = 2.10 ns가 고정 비용**이다. 주기를 줄여도 이 2.10 ns는 줄지 않는다.

### 3.2 PIPELINE (5단, ZeroE 수정 전, `1020_RISC_PIPELINE`)

Harris & Harris 7.5 구조. IF / ID / EX / MEM / WB, 포워딩(MEM→EX, WB→EX), lw-use 1 cycle stall, 분기는 EX에서 해결(taken 시 2 cycle flush). CONTROLLER는 단일 사이클과 동일.

| 주기 | setup slack | hold slack | cell area (µm²) | 동적 + 누설 (mW) | 1위 경로 endpoint |
|---:|---:|---:|---:|---:|---|
| 3.0 | 0.00 | 0.11 | 23,327 | 3.331 + 1.309 | RD2E_reg |
| 2.5 | 0.00 | 0.15 | 25,212 | 3.539 + 1.388 | PC_reg |
| 2.2 | 0.00 | 0.15 | 25,380 | 4.116 + 1.366 | ImmExtE_reg |
| **2.1** | **0.00** | 0.15 | **25,491** | **4.288 + 1.388** | PC_reg |
| 2.0 | −0.13 | 0.15 | 25,830 | | ImmExtE_reg |
| 1.9 | −0.16 | 0.15 | 22,694 | | RD1E_reg |
| 1.8 | −0.28 | 0.11 | 22,630 | | RD1E_reg |

- **선언 가능 주기 2.1 ns (476 MHz)**.
- **Critical path** (P2.2 리포트 기준, 모든 주기에서 같은 계열):

| 구간 | 누적 (ns) | 소요 |
|---|---:|---:|
| Rs2E_reg clk→Q | 0.15 | 0.15 |
| 포워딩 비교 `Rs2E == RdM` → select | 0.57 | 0.42 |
| 포워딩 3:1 mux | 0.80 | 0.23 |
| ALU 32b 뺄셈 | 1.47 | 0.67 |
| ZeroE (OR 트리) | 1.81 | 0.34 |
| PCSrcE → FlushE → 레지스터 D | 2.08 | 0.27 |

- endpoint가 PC_reg, ImmExtE_reg, RD2E_reg로 주기마다 바뀌는 것은 모두 **PCSrcE의 팬아웃**(PC mux, FlushD, FlushE)이기 때문이다. 병목은 "EX에서 분기를 해결하는 경로" 하나다.

### 3.3 PIPELINE + ZeroE 수정 (`1020_RISC_PIPELINE_ZEROE`)

수정은 CORE.v 한 줄이다.

```verilog
// 전: wire ZeroE = (ALUResultE == 32'd0);
wire ZeroE = (SrcAE == SrcBE);
```

- **의도**: BEQ의 분기 판정을 뺄셈 결과가 아니라 비교기로 한다. 비교기가 ALU와 병렬로 돌아 위 표의 "ALU 0.67 + ZeroE 0.34"가 비교기 하나(약 0.35 ns 예상)로 바뀐다.
- **규칙**: 포트 변경 없음, BEQ 의미("두 레지스터가 같으면 분기") 그대로, CONTROLLER 무수정.
- **기능 검증 (완료)**: 로컬 ModelSim에서 69/69 PASS (4 프로그램 × 16 case, 리셋 재인가, 해저드 시험). **cycle 수가 수정 전과 전부 동일**하다 (12,170.1 / 929.2 / 821.4 / 636.2).
- **합성 (완료, 2026-11-10 서버)**: 4자리 리포트.

|---:|---:|---:|---:|---:|
| 2.1 | 0.0015 | 0.1458 | 24,501 | 4.287 + 1.306 |
| 2.0 | 0.0037 | 0.1509 | 21,558 | 5.507 + 1.194 |

- **선언 가능 주기 1.7 ns (588 MHz)**. 1.6 ns는 0.0216 ns 모자란다 (그 netlist의 한계는 약 1.622 ns).

## 4. 파이프라인으로 얻은 것과 잃은 것

`int8_opt64` 기준, SINGLE 4.0 ns 대 PIPELINE 2.1 ns.

| 항목 | SINGLE | PIPELINE | 변화 |
|---|---:|---:|---|
| 최소 주기 | 4.0 ns | 2.1 ns | **f 1.90배** (얻음) |
| 평균 cycle | 677.9 | 821.4 | +21 % (잃음) |
| **T = cycle / f** | 2.712 µs | **1.725 µs** | **−36 %** (얻음) |
| CPU cell area | 17,397 µm² | 25,491 µm² | +47 % (잃음) |
| A 합계 (메모리 포함) | 76,779 µm² | 84,872 µm² | +10.5 % |
| CPU 전력 | 2.996 mW | 5.676 mW | +89 % (잃음) |
| P 합계 (메모리 포함) | 5.004 mW | 8.405 mW | +68 % |
| FF 수 | 1,024 | 1,502 | +478 |

**얻은 것**
- 입력 delay와 출력 delay가 한 경로에 겹치지 않는다. 포트가 모두 레지스터 직결이라 고정 비용 2.10 ns가 사라지고 주기를 내부 논리가 정한다.
- store 신호(`ALURESULT/WRITEDATA/MEMWRITE`)가 레지스터 출력이라 한 cycle 동안 안정적이다.

**잃은 것**
- **cycle +21 %**: 증가분 143.5 cycle 중 140.5가 taken 분기 flush(2 cycle씩)이고 3이 파이프라인 채움이다. lw-use stall은 ASM 배치로 0회.
- **면적 +47 %**: 파이프라인 레지스터 478개와 포워딩 mux, flush 게이트.
- **전력 +89 %**: f가 1.9배라 동적전력이 비례해 늘었다. 전력의 74 %가 clock network(FF clock 핀)이다.
- 메모리 동적전력도 f에 비례해 늘어난다 (P_mem 2.008 → 2.729 mW).

**왜 f가 5배가 아니라 1.9배인가**: EX 단이 포워딩 → ALU → Zero 판정 → PC 선택 → flush를 한 cycle에 한다. 단일 사이클 데이터패스에서 디코드와 레지스터 읽기만 빠진 길이다.

## 5. 조합별 T / A / P

A = CPU cell area + IMEM 매크로 + DMEM 50,667.68. P = CPU 전력 + 메모리 전력(계약 산식).
"내부 점수"는 이 표 8행 안에서의 최솟값을 best로 둔 `12.5·T_best/T + 6.25·A_best/A + 6.25·P_best/P`다. **다른 팀 값이 없으므로 실제 점수가 아니라 우리 선택지끼리의 상대 비교**다.

| CPU | 프로그램 | cycle | T (µs) | A (µm²) | P (mW) | 내부 점수 (T / A / P) |
|---|---|---:|---:|---:|---:|---|
| SINGLE 4.0 ns | baseline | 8,135.7 | 32.543 | 76,779 | 4.800 | 13.01 (0.51 / 6.25 / 6.25) |
| SINGLE 4.0 ns | int8_small | 729.5 | 2.918 | 76,779 | 4.986 | 17.99 (5.72 / 6.25 / 6.02) |
| SINGLE 4.0 ns | int8_opt64 | 677.9 | 2.712 | 76,779 | 5.004 | 18.40 (6.16 / 6.25 / 5.99) |
| SINGLE 4.0 ns | int8_fast | 552.5 | 2.210 | 95,417 | 6.629 | 17.11 (7.56 / 5.03 / 4.53) |
| PIPE 2.1 ns | baseline | 12,170.1 | 25.557 | 84,872 | 8.956 | 9.66 (0.65 / 5.65 / 3.35) |
| PIPE 2.1 ns | int8_small | 929.2 | 1.951 | 84,872 | 8.398 | 17.78 (8.56 / 5.65 / 3.57) |
| PIPE 2.1 ns | int8_opt64 | 821.4 | 1.725 | 84,872 | 8.405 | 18.91 (9.68 / 5.65 / 3.57) |
| PIPE 2.1 ns | **int8_fast** | 636.2 | **1.336** | 103,511 | 11.220 | **19.81** (12.50 / 4.64 / 2.67) |

읽는 법
- **ASM의 효과가 가장 크다.** 같은 CPU에서 baseline → opt64로 T가 1/12, 1/15가 된다.
- **파이프라인은 T를 얻고 A·P를 내준다.** 내부 점수 차이는 1~2점 수준이라, 다른 팀이 T를 얼마나 줄였는지에 따라 유불리가 갈린다.
- **전력이 파이프라인의 약점이다.** CPU 전력이 기본 활동률 추정이라 SAIF를 넣으면 달라질 수 있고, clock gating(`synth.tcl`의 `GATE_CLK`)이 다음 레버다.
- 단일 사이클 `int8_opt64`의 cycle은 ISA 모델 값이다 (단일 사이클은 1명령 = 1 cycle이고, 나머지 3개 프로그램은 RTL과 정확히 일치).
- 파이프라인의 load+store 횟수는 `MEMORY_POWER.v`가 IF 단의 opcode로 세기 때문에 stall·flush된 명령까지 포함한다 (opt64 55 → 63.8). 실제 DMEM 접근은 같다.
