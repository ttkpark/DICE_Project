# Project 1 R1.4 진행 상황과 PPA 개선 분석

분석일: 2026-11-09. 대상은 현재 로컬 R1.4 소스, 팀원의 어셈블리, 기존 서버 결과 정리 문서다. 원본 RTL·어셈블리·공통 측정 코드는 변경하지 않았다.

**판단:** 큰 소프트웨어 개선은 이미 달성했다. 현재 기록에서 가장 빠른 조합은 EX + fast이며, 64-word IMEM을 유지하는 주력 비교 후보는 EX + opt64다. 다음에는 EX 구조의 분기 판단 경로와 반복 JAL 비용을 줄이는 실험이 유망하다. ID 구조는 사이클 수가 적지만 현재 통과 주기가 길어 시간에서 불리하다. 최종 점수는 공식 PASS 팀의 항목별 최솟값을 알아야 확정된다.

- 팀 인수인계, ASM 최적화 보고서, baseline·small·opt64·fast의 소스·HEX와 기존 기능 결과.
- 최신 `EX_ID_PPA_COMPARE_20261109.md`의 여섯 서버 결과.

이전 인수인계의 R1.3a 설명과 미측정 표시는 역사 기록으로 읽어야 한다. 현재 제출·측정 조건은 R1.4이며, 최신 비교 문서에는 그 이후 서버 실행 결과가 기록돼 있다.

## 2. 파이프라인 진행 상황

단일 사이클 백업에서 IF/ID/EX/MEM/WB의 5단 구조로 발전했고, EX 분기판과 ID 분기판을 비교한 상태다. TOP의 외부 INSTR·READDATA 연결과 CPU-only 메모리 경계는 구현돼 있으며 CONTROLLER는 필수 8개 명령을 디코딩한다.

| 항목 | EX 분기판 | 현재 ID 분기판 |
|---|---|---|
| BEQ·JAL 결정 | EX | ID |
| 이동 시 후속 명령 취소 | 2개 | 1개 |
| 전달 | MEM/WB → EX, WB → ID | 기존 전달 + EX/MEM → ID 비교 입력 |
| LW 직후 일반 사용 | 1 stall | 1 stall |
| LW 직후 BEQ | 1 stall | 2 stall |
| 현재 기록된 통과 주기 | 2.3ns | 3.0ns |

ID는 분기 취소를 줄이는 대신 EX의 ALU 결과를 ID 비교 입력으로 즉시 전달한다. 이에 따라 **EX 전달 선택 → ALU → ID 비교 → PC 선택**으로 이어지는 긴 경로가 생길 수 있다. 이는 주기가 길어진 합리적인 설명이지만, 실제 최악 경로인지는 서버 `setup.rpt`를 봐야 확정할 수 있다.

반면 EX판은 BEQ를 `ALUResultE == 0`으로 판단한다. SUB의 결과에서 zero를 검사하는 경로이므로, 전달된 두 피연산자를 직접 비교하는 별도 equality 경로를 실험할 가치가 있다. 합성기가 기존 회로를 이미 최적화했을 수도 있어 개선을 보장하지 않는다.

근거 위치: 현재 `CORE.v:123`부터 load hazard, `:148`부터 EX/MEM→ID 전달, `:184`부터 redirect·flush. EX 백업 `:163`부터 ALU, `:173`부터 분기 판단, `:251`의 load-use 검사.

## 3. 명령어·프로그램 최적화 진행 상황

baseline은 각 가중치의 절댓값만큼 덧셈을 반복하고, 곱 32개를 SCRATCH에 저장했다가 다시 읽는다. 개선본은 X의 비트 한 번 검사를 네 출력에 공유하고, W를 두 배씩 키우며 직접 누산한다. X의 bit 7은 음의 가중치로 빼서 signed INT8을 처리한다. 누산기는 BIAS로 시작하며 SCRATCH를 쓰지 않는다.

이번에 기능 모델로 직접 다시 확인한 결과:

| 프로그램 | HEX word | 평균 실행 ISA 명령 수 | 실제 실행 load/store | 공개 기능 모델 |
|---|---:|---:|---:|---|
| baseline | 57 | 8,135.6875 | 110 / 37 | 16/16 PASS |
| small | 48 | 729.5000 | 50 / 5 | 16/16 PASS |
| opt64 | 58 | 677.8750 | 50 / 5 | 16/16 PASS |
| fast | 192 | 552.5000 | 50 / 5 | 16/16 PASS |

네 프로그램 모두 소스를 다시 조립한 결과가 저장된 HEX와 일치함도 확인했다.

opt64는 baseline보다 평균 명령 수 **91.67% 감소**, load+store **147→55회, 62.59% 감소**다. 이 값은 소프트웨어 실행량 개선이며, 같은 비율의 실제 시간·평균전력 개선을 뜻하지 않는다.

opt64는 2비트 부분 전개, 외부 루프·부호 처리 순서 개선, x0 기준 설정 읽기, load 직후 사용 회피를 적용했다. fast는 비트 코드를 전개하고 입력 두 개씩 처리해 분기 비용을 더 줄였다. 64-word 구간을 넘는 비용이 있어 fast의 낮은 cycle만으로 제출안을 결정하면 안 된다.

기존 ASM 보고서에서 opt64의 파이프라인 821.4는 당시 추정치다. 최신 비교 문서에는 EX 821.38, ID 751.12가 서버 결과로 기록돼 있다. 또한 “64-word의 한계”, “선택 명령은 무익”은 현재 알고리즘에 대한 판단이며, 모든 합법 RV32I 설계에 대한 증명된 하한은 아니다.

## 4. 서버 결과 기록과 해석

아래 수치는 기존 서버 요약 문서의 값이다. 면적과 전력은 SRAM 가산 후 총값이며, 전력은 배치·배선 전 추정 평균전력이다.

| 구조 | 프로그램 | 평균 cycle | 시간 [µs] | 총면적 [µm²] | 총전력 [mW] |
|---|---|---:|---:|---:|---:|
| EX 2.3ns | small | 929.25 | 2.1373 | 82,769.29 | 9.0957 |
| EX 2.3ns | opt64 | 821.38 | 1.8892 | 82,769.29 | 9.2206 |
| EX 2.3ns | fast | 636.25 | 1.4634 | 101,408.09 | 11.9036 |
| ID 3.0ns | small | 831.38 | 2.4941 | 82,103.94 | 7.6191 |
| ID 3.0ns | opt64 | 751.12 | 2.2534 | 82,103.94 | 7.7061 |
| ID 3.0ns | fast | 594.38 | 1.7831 | 100,742.74 | 9.7899 |

여섯 구성 모두 공개 CPU 16/16 및 선언 주기의 setup/hold PASS로 기록돼 있다. 이번 분석에서 원본 보고서를 독립 재검증한 것은 아니다.

- **EX 대 ID:** opt64에서 ID는 cycle이 약 8.6% 적지만, EX의 주기가 더 짧아 최종 시간은 EX가 약 16.2% 짧다. ID가 같은 opt64의 EX 시간을 따라잡으려면 주기가 약 **2.515ns 이하**여야 한다. fast는 약 2.462ns, small은 약 2.571ns다.
- **small → opt64:** EX에서 면적 구간을 유지하며 시간 11.6% 감소, 평균전력 약 1.4% 증가다. 현재 개선 중 비용 대비 효과가 분명한 결과다.
- **opt64 → fast:** EX에서 시간 22.5% 감소 대신 면적 22.5%, 평균전력 29.1% 증가다.
- **메모리의 비중:** EX opt64의 CPU cell area는 총면적에서 SRAM을 빼면 **23,388.11µm²**다. 총면적의 **71.7%**가 메모리 가산이다. 64→256-word 경계를 넘으면 **18,638.80µm²**가 증가한다. CPU를 10% 줄여도 총면적 감소는 약 2.8%이므로 코드 용량 경계가 중요하다.
- EX/ID는 목표 주기도 다르므로 면적·전력 차이를 분기 단계 변경 하나의 효과로 분리해 단정할 수 없다. 전력과 에너지(P×T)도 구별해야 한다.

## 5. 점수로 보면 무엇을 유지해야 하나

평가식은 `12.5×Tbest/T + 6.25×Abest/A + 6.25×Pbest/P`이며 각 비율 상한은 1이다. 여섯 후보만의 최솟값을 기준으로 계산하면:

| 조합 | 설명용 점수 /25 |
|---|---:|
| EX + fast | 21.56 |
| EX + opt64 | 21.05 |
| ID + opt64 | 20.55 |
| ID + fast | 20.22 |
| EX + small | 19.99 |
| ID + small | 19.83 |

**공식 성적 예측이 아니다.** 이 가정에서 EX fast의 opt64 대비 성능 이득은 +2.817점이지만, 면적 −1.140점·전력 −1.164점이 상쇄해 차이는 약 **0.514점**이다.

예를 들어 면적·전력 기준값은 이 표와 같고 다른 PASS 팀이 Tbest만 1.0µs로 낮춘다고 가정하면, EX opt64가 약17.98점, EX fast가 약17.60점으로 역전한다. 반대로 A/P 기준까지 달라지면 이 결론도 달라진다. 따라서 fast와 opt64 둘 다 최종 후보로 유지해야 한다.

평균전력 배점 때문에 최대로 빠른 주파수가 반드시 최고점은 아니다. 유력 후보의 주기를 몇 단계 늦춰 시간 손실과 평균전력·합성면적 이득을 함께 재측정할 가치가 있다. 기존 전력을 단순 주파수 비례 환산해 최종 결과로 쓰면 안 된다.

## 6. 추가 개선 실험의 우선순위

### 1) EX의 가짜 load-use stall 제거 + fast의 load 배치

EX 백업의 `lwStall`은 다음 명령의 rs1/rs2 비트를 opcode와 무관하게 읽는다. ADDI/LW에서는 immediate 비트를 레지스터 번호로 오인할 수 있다. 현재 ID판에는 실제 source를 사용하는 opcode만 검사하는 로직이 이미 있다.

ISA trace에서 fast는 `lw x4,4(x1)` 다음 `lw x5,4(x2)` 계열 때문에 불필요한 raw 의존이 **실행당 4회** 생긴다. 의미상 두 번째 LW는 x4를 읽지 않는다. source 사용 마스크를 EX판에 적용하면 평균 **636.25→632.25cycle**, 같은 2.3ns라면 약 **1.4542µs**가 예상된다. 첫 BIAS load 직후의 실제 의존도 독립 load와 재배치하면 1cycle을 더 줄일 후보다.

이는 ISA trace와 현재 제어 로직을 조합한 예상치다. 수정한 RTL의 기능·STA·power는 아직 측정하지 않았다. opt64에는 같은 가짜 의존과 인접 LW-use가 없어 이 수정의 주된 수혜는 fast다.

### 2) EX의 BEQ 독립 비교 경로

EX에서 전달된 두 피연산자를 직접 `==`로 비교해 BEQ 판단을 ALU SUB 결과의 zero 검사와 분리하는 실험이다. SUB→zero 경로를 줄일 수 있지만 실제 최악 경로가 다른 곳이면 주기가 개선되지 않는다.

가장 먼저 원본 `setup.rpt` 상위 경로를 보고 적용한다. 프로그램·cycle은 유지한 채 달성 주기와 CPU area·power를 비교한다. 비교기 추가 면적과 합성 최적화 결과까지 평가해야 한다.

### 3) BEQ는 EX에 두고 JAL만 ID에서 처리

ID판 전체를 채택하지 않고, 피연산자 비교가 필요 없는 무조건 점프만 일찍 처리하는 혼합 구조다. 현재 opt64는 DONE 이전 JAL을 평균 **27.375회**, fast는 **3회** 실행한다.

JAL penalty만 2→1이 되고 나머지 동작·주기가 같다는 가정에서 opt64는 **821.375→794.0cycle**, 2.3ns에서 **1.8262µs**, 약3.33% 시간 감소 후보다. 새 주기가 약 **2.379ns 미만**이면 cycle 이득이 시간에서도 남는다. fast의 같은 개선은 3cycle뿐이다.

이전 EX 분기와 더 어린 ID JAL이 동시에 이동할 때는 **이전 EX 분기가 우선**이어야 한다. JAL의 PC+4 link, 취소·stall 우선순위를 별도 검증해야 한다. 아직 구현·PPA 측정 전이다.

### 4) 중복 파이프라인 데이터와 불필요한 switching 축소

MEM/WB가 ALU/load/link의 32비트 값을 각각 저장한 뒤 선택한다. JAL의 link를 다른 결과 저장 경로와 합치거나 결과 선택 위치를 바꿔 FF를 줄일 수 있다. 다만 READDATA에는 고정 input delay 1ns가 있으므로 선택기를 MEM 쪽으로 옮기면 입력 timing이 나빠질 수 있다.

bubble 때 무효 제어는 확실히 내리면서 쓸모없는 데이터 갱신을 줄이는 방법도 전력 후보다. enable mux의 면적·지연·switching 비용이 있어 효과는 SAIF로 측정해야 한다. reset 의미, 유효 명령의 결과, 잘못된 store 차단은 유지한다.

### 5) 주기별 T/A/P 탐색

유력한 EX opt64/fast에 대해 예를 들어 2.3/2.5/2.7/3.0ns에서 공통 flow를 다시 실행한다. 주기를 바꿀 때마다 기능 activity부터 다시 만들어야 한다. 구조 효과를 분리해서 설명하려면 EX/ID를 같은 3.0ns에서도 한 번 비교한다.

파이프라인 자체의 개선 근거에는 단일 사이클 + 같은 opt64의 R1.4 측정도 유용하다. 현재 평균 ISA 명령 수 기준으로 단일 사이클이 EX opt64의 시간과 같아지는 주기는 약2.787ns다. 그 이상으로 느려도 면적·전력 이득이 점수에서 보상할 수 있으므로 실제 측정 없이 단일 사이클을 PPA 전체에서 열세라고 확정할 수 없다.

### 낮은 우선순위: 선택 BNE, shift, 큰 분기 예측기

표준 BNE를 지원하는 임시 기능 모델로 루프 치환을 시험했다. 원본 파일은 변경하지 않았다.

| 후보 | word | 평균 ISA 명령 | EX cycle 예상 | 확인 |
|---|---:|---:|---:|---|
| small + BNE | 47 | 681.5 | 865.25 | Python 공개16 PASS |
| fast + BNE | 191 | 549.5 | 631.25 | Python 공개16 PASS |

small+BNE는 기존 small보다64cycle 빨라져도 현재 opt64보다 느리다. fast+BNE는 약5cycle, 0.79% 개선이다. fast에 가짜 의존4회 제거·첫 BIAS load scheduling1회를 함께 적용하면 **626.25cycle 예상**이나, BNE RTL 구현·단독 시험·상용 PPA는 미완료다. opt64의 내부 루프는 단순 BEQ+JAL 쌍이 아니므로 바로 BNE 하나로 바꿀 수 없다.

`ADD w,w,w`를 `SLLI w,w,1`로 바꾸는 것은 1명령을1명령으로 바꾸므로 그 자체로 cycle을 줄이지 않는다. shift가 도움 되려면 알고리즘 변화까지 증명해야 한다. BNE와 shift의 의미·인코딩은 [공식 RV32I 명세](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html) 기준이며, 수업의 Harris 표B.1 허용 범위와 별도 단독 시험 조건도 지켜야 한다.

정적 backward-taken 예측은 중간 우선순위의 후속 실험이다. 큰 동적 예측기부터 추가하면 검증·면적 비용이 크고, IF에서 외부 INSTR를 해독해 목표를 만드는 경로는 고정 input delay와 함께 주기를 악화시킬 수 있다. 먼저 더 작은 수정의 효과를 확인하는 편이 타당하다.

## 7. 점수를 지키기 위한 결과 확인

다음은 새 규칙이 아니라 기존 R1.4 결과의 해석·재현에 필요한 확인이다.

1. 서버의 각 비교 폴더에서 RTL·SDC·프로그램·simulation_manifest·ppa_summary·ppa_status와 원본 timing/power/annotation 보고서를 함께 보관한다. 현재 로컬 설정과 서버 측정 설정을 혼동하지 않는다.
2. `read_saif` 성공이나 summary 생성만으로 annotation의 충분성을 보장하지 않는다. 공통 도구는 coverage 임계값을 자동 판정하지 않으므로 미주석 항목을 원본 보고서에서 확인해야 한다.
3. `timing_pass`는 최악 setup/hold slack을 검사한다. `check_timing`과 제약 보고서의 unconstrained path·transition 위반까지 함께 봐야 한다.
4. 공개 INT8 16개 PASS는 모든 기본 ISA·JAL link·illegal·중간 reset·hazard 조합의 시험을 대신하지 않는다. LW→BEQ, LW→SW, 최신 writer가 오래된 load를 덮는 경우, taken branch 뒤 SW 취소, x0, JAL link 직후 사용을 별도 확인한다.
5. `sim/MEMORY_POWER.v:49`부터의 load/store 계수기는 현재 TOP의 **IF INSTR opcode**를 센다. 파이프라인에서는 stall 중 같은 fetch와 나중에 flush될 fetch가 포함될 수 있어, 여기의 LOAD/STORE가 ISA 모델의 실제 실행50/5와 같다고 단정할 수 없다. 공식 TB를 임의 수정하지 말고 서버 manifest와 ISA trace 차이를 담당 조교에게 확인해야 한다. 이 차이를 무시해 CPU power를 역산해서는 안 된다.

최종 권고는 **EX fast와 EX opt64를 유지하면서, 가짜 stall 제거 → EX 분기 비교 경로 확인·개선 → JAL 조기 처리 → 소수 주기 sweep** 순서로 실험하는 것이다. 새 조합이 좋아졌다는 판단은 기능·동일 조건의 STA·총면적·총평균전력까지 갱신한 뒤 내린다.
