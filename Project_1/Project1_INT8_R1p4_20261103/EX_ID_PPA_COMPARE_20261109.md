# EX 분기·ID 분기 파이프라인 PPA 비교

- 정리일: 2026-11-09
- 대상: Project 1 INT8 선형계층 Release 1.4
- 비교 구성: **EX 분기 2.3ns**, **ID 분기 3.0ns** × small·opt64·fast
- 자료: 서버 공통 flow의 프로그램별 실행 완료 기록과 `ppa_summary.json` 터미널 요약

## 1. 주요 결과

- 여섯 조합 모두 공통 공개 기능 검사 **16/16 PASS**, 선언 주기의 **setup/hold PASS**를 확인했다.
- **실행시간이 가장 짧은 구성은 EX + fast**다: 1.4634µs.
- **64-word IMEM을 유지하는 성능 우선 후보는 EX + opt64**다: 1.8892µs, 총면적 82,769.29µm², 총전력 추정 9.2206mW.
- ID는 같은 프로그램에서 사이클 수가 적지만, 현재 통과한 주기가 길어 실제 실행시간은 EX보다 길다. 대신 평균전력과 총면적은 더 작다.
- 최종 PPA 점수는 다른 PASS 팀의 항목별 최솟값에 따라 달라진다. 이 문서의 비교용 점수를 공식 성적으로 해석하지 않는다.

## 2. 측정 조건과 프로그램

| 항목 | EX 분기 구성 | ID 분기 구성 |
|---|---|---|
| 파이프라인 | IF / ID / EX / MEM / WB | IF / ID / EX / MEM / WB |
| BEQ·JAL 판단 | EX 단계 | ID 단계 |
| 분기 이동 시 취소 | IF·ID의 후속 명령 두 개 | IF의 후속 명령 한 개 |
| 포워딩 | MEM·WB → EX, WB → ID | 기존 전달에 EX·MEM → ID 비교 입력 전달 추가 |
| LW 직후 일반 사용 | 한 사이클 stall | 한 사이클 stall |
| LW 직후 BEQ | 한 사이클 stall | 두 사이클 stall: MEM의 LW 결과는 WB까지 대기 |
| 인출 기본 진행 | PC+4, EX에서 이동 결정 시 수정 | PC+4, ID에서 이동 결정 시 수정 |
| 선언 클록 주기 | **2.3ns** | **3.0ns** |
| 주파수 | 약 434.78MHz | 약 333.33MHz |

공통 조건은 R1.4 TOP·메모리 경계, 기본 8개 ISA, 공개 16개 case, 공통 SDC와 SRAM 가산 산식이다. CPU만 합성하며 IMEM·DMEM은 외부 TB 모델이다.

**서로 다른 주기를 사용한 구성 비교**이므로, 표의 실행시간 차이를 분기 판단 단계 변경 하나의 효과로만 해석하지 않는다. 각 구조에서 현재 확인한 통과 설정을 비교한 것이며, 가능한 최소 주기를 모두 탐색한 결과도 아니다.

| 프로그램 | HEX word 수 | IMEM 비용 구간 | 변경 내용 |
|---|---:|---:|---|
| small | 48 | 64-word | 비트 하나씩 반복 처리, bias부터 직접 누산, 중간 곱 저장 제거 |
| opt64 | 58 | 64-word | 비트 두 개씩 루프를 펼쳐 반복 제어 감소 |
| fast | 192 | 256-word | 비트별 코드를 펼치고 입력도 두 개씩 묶어 반복 제어 감소 |

small·fast는 팀원 폴더의 `참고/1020_RISC_PIPELINE/sw/` 버전을 사용했다. `1020_RISC/sw/`의 동명 파일과는 종료부 load 배치가 다르므로 혼용하지 않는다. opt64는 `starter_giho/int8_opt64.hex`를 사용했다.

## 4. 결과 해석

### 4.1 같은 프로그램의 EX·ID 비교

아래 변화율은 **ID를 기준으로 EX가 어떻게 달라지는지**를 나타낸다.

| 프로그램 | EX의 실행시간 단축 | EX의 총면적 증가 | EX의 총전력 증가 |
|---|---:|---:|---:|
| small | 14.3% | 0.81% | 19.4% |
| opt64 | 16.2% | 0.81% | 19.7% |
| fast | 17.9% | 0.66% | 21.6% |

예를 들어 opt64에서 ID는 평균 751.12회, EX는 821.38회로 ID의 사이클 수가 더 적다. 그러나 EX의 한 사이클은 2.3ns, ID는 3ns이므로 실제 완료 시간은 EX가 약 16.2% 짧다.

따라서 **ID의 분기 취소 감소 효과는 존재하지만, 현재 설정에서는 EX의 짧은 주기 이득이 더 크다.** 반대로 ID는 동일 프로그램에서 더 낮은 평균전력을 보이므로 전력 측면의 대안으로 보관할 가치가 있다.

### 4.2 프로그램별 선택

- **small → opt64:** 같은 64-word IMEM을 유지하면서 반복 제어를 줄인다. EX에서는 시간 약 11.6% 단축·전력 약 1.4% 증가, ID에서는 시간 약 9.7% 단축·전력 약 1.1% 증가다. 총면적은 각 구조 내에서 같다.
- **opt64 → fast:** 더 짧은 실행시간을 얻는 대신 큰 IMEM의 면적·평균전력 비용을 지불한다.

| 구조 | fast의 실행시간 단축 | fast의 총면적 증가 | fast의 총전력 증가 |
|---|---:|---:|---:|
| EX | 22.5% | 22.5% | 29.1% |
| ID | 20.9% | 22.7% | 27.0% |

fast는 IMEM이 64-word에서 256-word 구간으로 바뀐다. 이때 메모리 가산 면적은 59,381.18 → 78,019.98µm²로 **18,638.80µm² 증가**한다. 실제 표의 면적 증가량도 이 값과 일치한다. IMEM fetch당 에너지 추정값도 2.23 → 7.00pJ로 바뀐다.

전력 P는 **평균전력**이고 에너지 P×T가 아니다. 실행시간을 줄였다는 이유만으로 전력 점수도 좋아지는 것은 아니다.

## 5. 채점 기준을 적용한 비교

[프로젝트 평가 계약](PROJECT_CONTRACT_KO.md)의 PPA 25점 산식:

```text
S25 = 12.50 × min(1, T_best / T)
    +  6.25 × min(1, A_best / A)
    +  6.25 × min(1, P_best / P)
```

`T_best`, `A_best`, `P_best`는 각각 **공식 PASS 팀의 항목별 최솟값**이다. 따라서 성능 배점이 크더라도 시간만으로 최종 우열을 확정할 수 없다. A·P는 CPU 단독값이 아닌 메모리 가산 후 총값이다.

### 여섯 조합만을 기준으로 한 설명용 계산

다음은 공식 성적 예측이 아니라 **이 문서의 여섯 조합에서만 최솟값을 잡은 비교용 계산**이다.

- T 기준값: 1.4634µs — EX + fast
- A 기준값: 82,103.94µm² — ID + small / opt64
- P 기준값: 7.6191mW — ID + small

| 조합 | 비교용 점수 [25점 만점] |
|---|---:|
| EX + fast | 21.56 |
| EX + opt64 | 21.05 |
| ID + opt64 | 20.55 |
| ID + fast | 20.22 |
| EX + small | 19.99 |
| ID + small | 19.83 |

이 가정에서는 EX + fast가 앞서고, EX + opt64와의 차이는 약 0.51점이다. **다른 팀의 최솟값이 달라지면 점수와 순위도 달라질 수 있다.** 이 숫자를 실제 획득 점수로 제출하지 않는다.

## 6. 현재 판단과 검증 범위

### 현재 판단

- **성능 우선 후보:** EX + fast. 현재 여섯 조합 중 실행시간이 가장 짧다.
- **작은 IMEM을 유지하는 주력 후보:** EX + opt64. fast보다 총면적·총전력이 작다.
- **더 낮은 평균전력의 대안:** ID + opt64. 현재 EX보다 느리지만 총면적·전력은 작다.
- small은 개선 효과를 설명하는 비교 기준으로 보관한다. 최종 제출 후보의 점수는 공식 평가 기준값을 고려해 판단한다.

### 검증된 사항과 남은 확인

- 확인: 여섯 구성의 공통 flow 정상 완료, 공개 기능 16/16, 선언 주기 setup/hold PASS, 프로그램별 PPA summary 생성·결과 보관.
- 이 문서는 **서버 터미널의 완료 기록·요약표를 정리한 문서**다. 서버의 모든 원본 보고서·SAIF를 별도로 전수 검토한 기록은 아니다.
- 전력은 SAIF 기반 CPU 보고서와 수업용 SRAM 동적·정적 가산값을 합한 **배치·배선 전 추정치**다. SAIF annotation 보고서의 상세 검토는 별도다.
- 공개 16개 결과는 공식 공개·숨김 24개 전체 평가를 대신하지 않는다.
- 명령어·RTL·주기를 바꾸면 같은 조건으로 기능 실행부터 다시 진행해 activity·합성·STA·전력을 갱신해야 한다.

## 7. 결과 보관 위치와 재현

서버 프로젝트 루트:

```text
/home/dice/dice003/Project1_INT8_R1p4_20261103/
```

결과 디렉터리 패턴(`*`는 실제 실행 시각):

```text
comparisons/ex_int8_opt64_*/
comparisons/ex_int8_fast_*/
comparisons/ex_int8_small_*/
comparisons/id_int8_opt64_*/
comparisons/id_int8_fast_*/
comparisons/id_int8_small_*/
```

각 폴더에서 확인할 항목:

- `results/ppa_summary.json`: 시간·면적·전력의 최종 집계
- `results/simulation_manifest.json`: 사용 프로그램·주기·소스 fingerprint·case별 사이클과 PASS 기록
- `results/ppa_status.json`: 정밀 setup/hold slack과 timing_pass
- `reports/setup.rpt`, `reports/hold.rpt`, `reports/cpu_area.rpt`: STA·CPU 면적
- `reports/<case>/power.rpt`, `reports/<case>/annotation.rpt`: case별 CPU 전력·SAIF annotation
- `logs/`: 기능·합성·변환 로그
- `rtl/`, `synth/`, `programs/`: 해당 실험 당시 보관한 CPU 소스·제약·프로그램

보관된 RTL과 SDC의 주기를 맞춘 뒤, 예를 들어 opt64를 재실행하는 명령:

```bash
python3 tools/run_flow.py sim --program programs/int8_opt64.hex
bash run_ppa.sh
```

기본 `run_sim.sh`는 baseline을 선택하므로, 프로그램을 비교할 때에는 위처럼 `--program`을 명시한다. 보고서의 수치를 재현할 때는 원본 결과 폴더의 소스·프로그램·제약과 manifest를 함께 대조한다.
