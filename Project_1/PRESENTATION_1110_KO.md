발표 슬라이드를 만드는 사람이 이 문서만 보고 숫자를 옮겨 쓸 수 있게 정리했다.
같은 내용을 보기 좋게 만든 페이지: [PRESENTATION_1110_KO.html](PRESENTATION_1110_KO.html) (브라우저로 열면 된다, 인터넷 없이도 열린다).
모든 측정값은 2026-11-10 ~ 11 수업 서버에서 R1.4 공통 flow(`run_sim.sh` → `run_ppa.sh`와 같은 명령)로 잰 **공개 16 case** 결과다. 공식 24 case 성적이 아니다.
같은 폴더의 `PRESENTATION_COMPARE_KO.md`는 R1.4 이전 flow로 잰 옛 자료라서 숫자를 이 문서와 섞어 쓰면 안 된다.

## 5. 주기를 결정하는 경로 (setup 보고서에서 확인)

| CPU | 주기 | 가장 느린 경로 | 도착 시각 |
|---|---:|---|---:|
| single | 3.82 ns | `INSTR` 입력 → 레지스터 읽기 → ALU 덧셈기 → `ALURESULT` 출력 | 2.7192 ns |
| ID | 2.36 ns | MEM 결과 → EX 포워딩 → ALU 뺄셈기 → ID 비교기로 포워딩 → 분기 판정 → PC 선택 → `PC` | 2.2077 ns |
| EX | 1.62 ns | `PCE` 레지스터 → 분기 목표 덧셈기 → PC 선택 → `PC` | 1.4653 ns |

- **single**: 입력 지연 1.00 ns와 출력 지연 1.00 ns가 한 경로에 같이 들어간다. 3.82 ns 중 공통 SDC가 가져가는 몫이 2.00 ns다.
- **ID**: 같은 cycle 안에 "EX의 ALU 결과 → ID의 같음 비교 → PC 선택"이 이어진다. 분기 손실을 1 cycle로 줄인 대가다.
- **EX**: 남은 경로는 레지스터에서 레지스터로 가는 덧셈기 하나다. ALU와 분기 판정은 더 이상 최악 경로가 아니다.

## 6. 발표에서 쓸 해석

아래 비교는 `int8_fastv2` 기준이다.

- **EX가 T에서 이긴다.** EX는 single보다 cycle이 14.3% 많지만 주기가 2.36배 짧다(3.82 → 1.62 ns). T는 2.06배 짧다.
- **ID는 cycle이 적어도 주기에서 진다.** ID는 EX보다 cycle이 6.0% 적지만 주기가 45.7% 길어서 T가 36.9% 길다(1.3980 대 1.0210 µs). 이유는 5장의 ID 경로다.
- **P는 EX가 가장 나쁘다.** single의 2.20배다. 클럭이 빨라진 만큼 초당 스위칭이 늘기 때문이다.
- **한 번 실행에 드는 에너지(P × T)는 셋이 비슷하다.** single 14.74 nJ, ID 16.04 nJ, EX 15.73 nJ. 채점 항목은 아니고 위 표에서 계산한 값이다.
- **256 구간 프로그램을 고른 이유.** EX에서 `int8_opt64v2` 대신 `int8_fastv2`를 쓰면 A가 22.8%, P가 30.0% 늘지만 T가 18.9% 줄고 T 배점이 A·P의 두 배다. 다만 v2로 차이가 좁혀져서(표 내 점수 19.47 대 18.85), A·P가 아주 작은 팀이 있으면 순서가 바뀔 수 있다.
- **v2의 효과는 분기가 많은 프로그램에서 크다.** `int8_opt64`는 EX에서 5.4% 줄었고, 이미 분기를 펼쳐 놓은 `int8_fast`는 0.9%만 줄었다. v2는 T와 P를 같이 줄이거나 P를 0.1% 안에서 유지한다.

## 7. 주기를 정한 방법

후보 주기마다 공식 `synth/run_ppa.tcl`과 같은 순서·같은 `compile`로 합성해 setup·hold slack이 둘 다 0 이상인 가장 짧은 주기를 골랐다(`compile_ultra`는 쓰지 않았다). 고른 주기로 공식 flow를 돌렸을 때 slack이 탐색 값과 소수 넷째 자리까지 같았다.

1차 탐색(0.05~0.30 ns 간격)에서 통과한 최소 주기는 single 3.90, ID 2.40, EX 1.70 ns였고, 그 아래를 0.02 ns 간격으로 다시 탐색했다.

| single 주기 | setup slack | 통과 | | ID 주기 | setup slack | 통과 | | EX 주기 | setup slack | 통과 |
|---:|---:|:---:|---|---:|---:|:---:|---|---:|---:|:---:|
| 3.90 | 0.0005 | O | | 2.40 | 0.0016 | O | | 1.70 | 0.0031 | O |
| 3.88 | 0.0020 | O | | 2.38 | 0.0008 | O | | 1.68 | 0.0007 | O |
| 3.86 | −0.0020 | X | | 2.36 | 0.0003 | O | | 1.66 | 0.0002 | O |
| 3.84 | −0.0037 | X | | 2.34 | −0.0006 | X | | 1.64 | −0.0014 | X |
| 3.82 | 0.0008 | O | | 2.32 | −0.0055 | X | | 1.62 | 0.0026 | O |
| 3.80 | −0.0000 | X | | 2.30 | −0.0019 | X | | 1.60 | −0.0000 | X |

hold slack은 모든 주기에서 0.1030 ns 이상이다.

통과가 주기 순서대로 나오지 않는 것(EX: 1.64 실패, 1.62 통과)은 합성이 목표 주기마다 다른 회로를 만들기 때문이다. 한계 근처에서는 slack이 0 주변 수 ps 안에서 흔들린다. 같은 RTL·같은 flow·같은 툴이면 결과는 재현된다. 실제로 11-10과 11-11 두 번의 실행에서 slack과 면적이 같았다.

주기는 소수 둘째 자리까지만 쓴다. TB 시간 단위가 1 fs라서 반주기가 fs로 나누어떨어져야 공식 flow의 "cycle × 주기 = 실행 구간" 검사를 통과한다.

## 9. 말할 때 조심할 것

- 숫자는 공개 16 case 기준이다. 공식 성적은 비공개 8개를 더한 24 case로 따로 나온다.

- 기본 8명령만 구현했다. 선택 확장 명령과 M 확장은 쓰지 않았다.
