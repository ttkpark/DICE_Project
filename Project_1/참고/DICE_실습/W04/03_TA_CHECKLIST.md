# 조교 체크포인트

| 확인 순서 | 학생이 보여 줄 것 | 통과 조건 |
|---|---|---|
| 1 | 본인 `todo/checkpoint/rtl/alu.v` | CP01~CP12 작성, 포트·폭 유지, case의 모든 결과 대입 |
| 2 | 해당 폴더에서 새로 실행한 검사 | 컴파일 성공, T01~T34 OK, 최종 PASS, FAIL 없음 |
| 3 | T21의 코드·입력·출력 | 음수가 양수보다 작다는 것과 overflow 보정의 역할 설명 |
| 4 | T27 또는 T32 | 왜 36칸이 아니라 4칸 이동하는지 설명 |
| 5 | 소스·TB·로그·파형 | 실제 실행에 사용한 파일의 위치와 보관 상태 확인 |

구두 질문은 다음 두 문장으로 제한하여 길게 암기시키지 않음.

- “`80000000`을 signed로 읽으면 음수인데, 왜 감산 결과의 맨 앞 비트만 보면 비교가 틀릴까요?”
- “B가 `00000024`일 때 몇 칸 이동하나요? 코드의 어느 부분 때문에 그런가요?”

조교용 핵심 답: 첫 사례는 32비트 감산 overflow로 부호가 뒤집혀 `sum32[31] ^ v_raw` 보정 필요. 두 번째는 `b[4:0]`만 사용하므로 4칸 이동.

통과 여부는 소스 확인과 새 실행 결과로 판단. 코드 캡처만 제출하거나 과거 PASS 로그만 제시한 경우 완료로 처리하지 않음. 온라인 수업에서는 화면 공유 또는 해당 소스·로그·VCD 또는 FSDB 제출로 확인. 하드웨어 보드 사진은 요구하지 않음.

## 새 검사 확인

학생 본인의 `~/DICE/W04/todo/checkpoint`에서 다음 순서로 확인합니다.

```bash
pwd # 학생 본인의 checkpoint 위치 확인
cat rtl/alu.v # CP01~CP12와 포트 및 case 확인
bash 01_run_alu_check.sh # 학생 코드로 새 VCS 검사 실행
cat logs/alu_check.log # T01~T34 OK와 정확한 최종 PASS 및 FAIL 부재 확인
bash 01_view_alu_check.sh # T21 및 T27/T32 파형 확인
```

T21은 200~210 ns, T27은 260~270 ns, T32는 310~320 ns 구간입니다.
34개 자동검사는 result와 zero만 판정합니다. 내부 c/v/v_raw와 코드 설명은 따로 확인합니다.
고정 TB의 기대값 변경이나 검사 삭제는 완료로 인정하지 않습니다.
